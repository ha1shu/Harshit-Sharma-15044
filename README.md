# Multiplex Ticket Counter

A small multiplex ticket-counter application.

It has:

- Staff login
- Dashboard with shows, sales, revenue, and seat availability
- New booking page
- Decimal-based ticket pricing
- Festival and membership discounts
- PostgreSQL database storage
- Booking history and invoice pages
- Admin tools for shows, prices, and offers
- CSV import for seat-tier prices
- Docker Compose setup

The app uses simple server-rendered HTML pages and a FastAPI backend.

## Main Technologies

- Python 3.12
- FastAPI
- SQLAlchemy 2.0
- PostgreSQL 16
- Alembic migrations
- Psycopg PostgreSQL driver
- Pytest
- Docker Compose

## Quick Start With Docker

From the project root:

```bash
docker compose up -d --build
```

I Open the application In my local System:

- Main app: http://127.0.0.1:8000/login
- Dashboard: http://127.0.0.1:8000/dashboard
- Admin: http://127.0.0.1:8000/admin
- API health check: http://127.0.0.1:8000/health

The API container automatically:

1. Runs the Alembic migrations.
2. Adds demo cinema, show, tiers, and users.
3. Starts Uvicorn.

Demo login:

```text
Username: staff
Password: admin123
```

The Docker database uses a named volume called `multiplex_pgdata`, so data stays after a normal container restart.

## Stop the App

```bash
docker compose down
```

To also delete the local database data:

```bash
docker compose down -v
```

This removes all local bookings and database records.

## Run Without Docker

You still need a running PostgreSQL database.

Create the Python environment:

```bash
cd backend
python3.12 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
```

Set the database URL:

```bash
export DATABASE_URL=postgresql+psycopg://postgres:postgres@localhost:5432/multiplex
```

Run the migration and demo seed:

```bash
PYTHONPATH=. python -m alembic upgrade head
PYTHONPATH=. python -m scripts.seed
```

Start the API:

```bash
PYTHONPATH=. uvicorn app.main:app --host 0.0.0.0 --port 8000
```

## Database

The database uses PostgreSQL. SQLite is not used for database tests or production-like behavior.

Main tables:

- `cinemas`
- `screens`
- `movies`
- `tax_configs`
- `shows`
- `seat_tiers`
- `offers`
- `users`
- `bookings`
- `booking_items`
- `booking_offers`

Money values use PostgreSQL `NUMERIC` columns and Python `Decimal`. Do not use floats for money calculations.

Useful database commands:

```bash
cd backend
. .venv/bin/activate

# Show the current migration
PYTHONPATH=. python -m alembic current

# Apply all migrations
PYTHONPATH=. python -m alembic upgrade head

# Roll back one migration
PYTHONPATH=. python -m alembic downgrade -1
```

Create a new migration after changing models:

```bash
PYTHONPATH=. python -m alembic revision --autogenerate -m "describe change"
```

Always review an autogenerated migration before applying it.

## Pricing Rules

The pricing engine is in `backend/app/pricing/engine.py`.

The calculation order is:

1. Add ticket line items to get the subtotal.
2. Apply the flat festival discount.
3. Apply the membership percentage discount.
4. Apply the membership discount cap.
5. Add the convenience fee per ticket.
6. Calculate GST on the discounted subtotal plus the fee.
7. Round money values to two decimal places.

The engine is separate from the database. This makes it easy to test and keeps pricing rules predictable.

## Booking Flow

When staff confirms a booking:

1. The browser loads the selected show from the API.
2. The API reads prices from the database instead of trusting browser prices.
3. Seat-tier rows are locked with a database row lock.
4. The API checks available seats.
5. The pricing engine calculates the invoice with `Decimal`.
6. The booking and booking items are saved.
7. Available seats are reduced in the same transaction.
8. The browser opens the saved invoice.

If there are not enough seats, the transaction is rolled back and the user sees an error.

## CSV Seat-Tier Import

The Admin page accepts a CSV with these columns:

```csv
tier_name,price
Silver,₹120
SILVER,"1,200.50"
Gold,Rs. 220
Complimentary,0
```

Import behavior:

- Tier names are trimmed and stored in Title Case.
- Matching is case-insensitive.
- Currency symbols, `Rs.`, `INR`, spaces, and commas are removed from prices.
- Blank, negative, invalid, and non-finite prices are rejected.
- The last valid duplicate row wins.
- The preview shows imported rows, duplicate winners, and rejected rows.
- The database is not changed until the user checks the confirmation box and clicks `Apply prices`.
- Existing tiers are updated instead of duplicated.

When a new tier is created from a price-only CSV import, its seat capacity starts at zero. Set its capacity separately before selling seats.

## Testing

Run all tests:

```bash
cd backend
. .venv/bin/activate
PYTHONPATH=. pytest -q
```

Run only pricing tests:

```bash
PYTHONPATH=. pytest -q tests/test_pricing_engine.py
```

Run only CSV import tests:

```bash
PYTHONPATH=. pytest -q tests/test_seat_tier_import.py
```

The test suite checks:

- Pricing totals and rounding
- Discount order and caps
- Invoice line-item totals
- Mixed-case CSV duplicates
- Last-valid duplicate behavior
- Blank prices
- Negative prices
- Invalid prices
- Valid zero prices

Database smoke checks should use PostgreSQL, not SQLite:

```bash
docker compose up -d db
cd backend
. .venv/bin/activate
DATABASE_URL=postgresql+psycopg://postgres:postgres@localhost:5432/multiplex PYTHONPATH=. python -m alembic upgrade head
```

```bash

```

Read API logs:

```bash
docker compose logs --no-color --tail=100 api
```

Read database logs:

```bash
docker compose logs --no-color --tail=100 db
```

Check the API:

```bash
curl http://127.0.0.1:8000/health
```

Check a page:

```bash
curl -I http://127.0.0.1:8000/dashboard
```

Check a show and its seat tiers:

```bash
curl http://127.0.0.1:8000/api/shows/1
```

Check saved bookings:

```bash
curl http://127.0.0.1:8000/api/bookings
```

If port `8000` is already in use:

```bash
lsof -nP -iTCP:8000 -sTCP:LISTEN
```

Stop the old Uvicorn process or change the host port in `docker-compose.yml`.

If the API restarts during startup, check the logs. The API waits for PostgreSQL health before starting migrations, but the first database start can still take a few seconds.

If the browser shows old CSS, use a hard refresh:

```text
Ctrl+Shift+R
```

## UI Pages

- `/login`: staff login
- `/dashboard`: sales summary, show schedule, and availability
- `/booking`: select seats and create a booking
- `/booking-confirmation?id=1`: saved invoice
- `/bookings-history`: saved booking list
- `/admin`: show setup, tier prices, offers, and CSV import

The UI uses a light background with a crimson red accent. The layout works on desktop, tablets, and small screens.

## Common Development Rules

- Keep pricing code pure and separate from HTTP and database code.
- Use `Decimal` for all money values.
- Use database transactions for bookings and seat changes.
- Do not update seats outside the booking transaction.
- Add tests when changing pricing, imports, database behavior, or API contracts.
- Keep user errors visible in the page; do not fail silently.
- Run the focused test first, then run the full test suite before finishing.
